# Jev × three-vrm

文本驱动的角色表演管线 demo（一期）。

```
        输入层                          判断层
文本 → DeepSeek ──→ 台词 ──→ 立刻开口（带着第一反应）
  │     说什么         └──→ Jev ──→ 每一段换成它判断的情绪
  │                          怎么演（一句话按句分段）
  └──→ Jev：听到这句话的第一反应（和写台词并行）
```

两层天然串行 —— Jev 判断的对象就是 DeepSeek 写出来的那句话，没有它无从判断。
既然不能并发，就让**说话别等判断**：台词一到就开口并套用基线表演，Jev 的结果
晚几百毫秒回来，再替换掉还没触发的节拍。实测感知延迟从 1.97s 降到 1.28s，
省掉的正好是判断层那一段。

二期把输入层换成 gpt-live-1 的实时语音，**右边全不动** ——
Act IR 的时间锚点本来就是为"决策时还不知道音频时长"设计的，
渐进升级需要的也正是这套锚点。

## 跑起来

```bash
npm install && npm run dev
```

模型已放在 `public/models/`，无需额外下载。

背景（面板"模型"下面的"背景"，跟着角色记在浏览器里，见"模型"一节）：**公园**（默认，`vrm/scenes/park.ts`）、**咖啡店**（`vrm/scenes/cafe.ts`）、**街景**（海边小镇，`vrm/scenes/street.ts`）或原来的纯色渐变。

- 试过把桌椅、吊灯、绿植、墙地面换成 Poly Haven 的写实模型和 PBR 材质：和动漫角色放在一起非常突兀，撤掉了，
  只留下打光

公园是全 3D 的（`vrm/scenes/park.ts`），照着一张实拍的公园照片搭：木栈道从她脚下的平台出发弯着伸进远处
（三条路都一直伸到 150m 外的雾里，转到哪个方向都看不到路的尽头），两边草坪、大树、灌木、欧式路灯、青苔石头，
近景一簇簇白、蓝、黄的小花（ez-tree 演示场景里的花，随风摆）。

- **树和灌木**：[ez-tree](https://github.com/dgreenheck/ez-tree)（npm `@dgreenheck/ez-tree`，MIT）程序生成 ——
  真实的树皮贴图、一片片的叶子卡片、自然分叉，叶子随风轻轻摆。一棵大树 1.4 万~2.2 万个三角形、生成 6~30ms；
  生成 5 个变体（白蜡、橡树，叶子加到 1.4~1.5 倍），近处 81 棵 + 远处一圈 100 棵 + 灌木 23 丛共用几何体。
  模块 4MB（树皮和树叶贴图打包在里面），只在选了公园时才动态加载。
  - **合批**：同一个变体的树干、树冠各合成一个 InstancedMesh（路灯同理），每次渲染前在 CPU 上按视锥逐棵剔除，
    只把看得见的写进实例缓冲 —— 合批之后 three 只能整体剔除，不逐棵剔的话镜头背后的树也照画，三角形反而翻倍。
    投影的另用一个 InstancedMesh、只在阴影通道里画，而且只画影子落得进画面的：树冠沿着阳光扫到地面是一条胶囊，
    整个在视锥外就跳过。树和灌木从每帧 188 次绘制降到 30 次左右，阴影通道的三角形少一大半，逐像素对比画面完全一样
  - **逆光透光**（假的次表面散射，写法参考 Stillwater）：在 ez-tree 树叶材质的 onBeforeCompile 后面再串一段，
    视线对着太阳、叶子背面朝着太阳时透出暖黄绿的光，乘上太阳的阴影（树冠里面暗下去，留 25% 当天光）。
    正对太阳时树冠亮两成多，顺光看不变；原来补的自发光从 0.55 降到 0.3，只托底
  - **影子跟着风摆**：树叶和投影的花各配一个深度材质，注入和颜色材质同一段风的代码、读同一个 uTime。
    不配的话 three 用自己的（静止的）深度材质画阴影，树在摇、地上的影子不动
- **草坪**：近处 1.6 万丛 3D 的草（ez-tree 演示场景里的草丛模型 `public/scene/eztree/grass.glb`，MIT），
  越靠近角色越密，也随风摆；远处铺 Poly Haven 的草地材质（Aerial Grass Rock，往鲜绿拉了一点）
- **近处**：旧木平台和栈道（Weathered Brown Planks，漫反射 + 法线 + AO/粗糙度）、8 盏欧式路灯（Street Lamp 01）、
  青苔石头（Rock Moss Set 01 里挑几块，原尺寸 2~3m，缩到半米到一米）、树桩凳和长凳、落叶
- **光**：舞台的主光当太阳用（`Backdrop.sun`）：右侧偏前、离地约 43°、暖白 2.2，投软阴影（覆盖身边 ±18m，
  树冠的影子落在栈道和草地上，平台上空留了一块树冠的空隙让阳光照进来）。补光、轮廓光调弱（0.25 / 0.35），
  半球光 0.42，环境光（名古屋公园全景的 1k HDR，只用来打光）0.2；雾从 20m 开始、和地平线同色。踩过的坑（逐个量过）：
  - 另加一盏从身后照来的太阳（照片里是逆光）：three.js 的灯没法只照场景、不照角色，太阳 2.2 照在脸上，脸发白、
    五官的明暗全没了
  - 舞台主光不投影、太阳投影：主光从正面把平台照亮，太阳的影子被冲淡到看不出来
  - 主光在右前方 37°（顺光）：影子都落在人和凳子正后方，从正面看被挡住
  - 补光、轮廓光、半球光、环境光都不投影，加起来比太阳还亮：平台上的影子只比旁边暗一成多。
    这张 HDR 是阳光下的树林，环境光 0.3 时单它照在平台上就和太阳一样亮
  - 树叶、草补了一点自发光，画面不至于因为环境光压低而整体发暗（只加在它们自己身上，不冲淡地上的影子）
- **林间光柱（丁达尔效应）+ 光里的尘埃**（`vrm/scenes/sunlight.ts`）：沿阳光方向的 15 根半透明光柱，从树冠里斜着漏下来，
  加色混合、边缘柔和，一束里再分出几道细光、带一点缓慢流动的明暗；光柱里和平台四周飘着约 1000 颗尘埃，慢慢漂、一闪一闪。
  光柱是绕自身轴转向相机的长条面片（从哪个角度看都像一束体积光），全部一个 InstancedMesh，尘埃一个 Points，各一次绘制。
  - 半身景别是长焦（24°），只看得到她身后很窄的一条：近处的光柱放两侧，头后面那块的压暗（脸的对比要留着）；
    最亮的一段在离地 3~6m，衬着暗绿的树叶最显 —— 贴地那段叠在亮的雾上只会糊成一团白
  - 雾别太白、要带点饱和度：太白的话画面发灰发白，光柱也衬不出来
  - 光柱和尘埃用滤色（screen）混合，不用加色：宽屏转到太阳那一侧时，雾 + 天空光晕 + 几根光柱用加色会叠成一片乳白；
    滤色在亮的底色上只加一点，衬着暗绿的树叶才显出来
  - 没用路径追踪 / 屏幕空间体积光：角色是动的（呼吸、头发弹簧、风里的草），逐帧累积的路径追踪一动就满屏噪点，
    MToon 也进不了路径追踪器；屏幕空间的体积光要太阳在画面里，这里太阳在相机右后方
- **背面**（她面朝的那一侧，镜头转到身后才看到）：路两边一片树林、远处一圈加密的树、灌木、花丛、两张铸铁扶手的木长椅（面朝栈道）。
  第一版这边只有一条路和几盏灯，转过去很空。用单独的随机数生成，正面已经调好的树、草、花位置不受影响
- **云**：天空球前面一圈 16 片半透明的积云（canvas 画的），哪个方向看都不是一片空天
- 头后面不放树干和灯杆（视线走廊，和咖啡店"头后面留空"同一个道理）
- **开销**（Retina 大窗口、画布 2232×1960 时量的）：每帧 320~330 次绘制、140 万~200 万个三角形
  （合批之前约 500 次、260 万~300 万），其中角色自己约 200 次（VRM 的各个部件 + 描边 + 阴影）。不用后期处理
  - 像素预算（`Backdrop.pixelBudget`，公园 340 万像素）：大窗口时像素比自动从 2 降到约 1.76，GPU 每帧少 3~4ms ——
    满屏逐像素算光的树叶和草，开销跟着像素数走。dpr 1 的屏幕、小窗口不受影响，咖啡店和纯色背景不设预算
  - 透光每帧多约 0.5ms、随风的影子多约 0.4ms（GPU，交替开关量的），比像素预算省下的少得多
  - 量 GPU 时间要用 `EXT_disjoint_timer_query_webgl2`：`gl.finish()` 包住渲染量出来的只是 CPU 提交的时间
    （ANGLE / Metal 下 finish 不等 GPU 做完），量到 1.3ms 时 GPU 其实要 8~20ms
  - 以后还能省的：远处那一圈树做多角度贴图（impostor）；手机上再压像素预算
- 试过、换掉的两版：全程序生成（几何体 + canvas 画的叶子贴片，树冠一团一团的，很假）；
  Poly Haven 的公园全景照片投影成地面和天空（`GroundedSkybox`，远景就是一张图，太糊，近处的树干转到背面还会被压扁在地上）。
  Poly Haven 自己的树模型太重（一棵阔叶树 170 万~470 万个三角形），网页里放不了几十棵

街景是全 3D 的（`vrm/scenes/street.ts`），照着一张二次元风格的海边小镇插画搭：她站在路上靠左那条车道，
身后左边是一排两三层的日式小楼（咖啡店、陶器店、土特产店、居酒屋、住家），右边是人行道、花岗岩矮墙、铁栏杆和海，
路过了人行横道往左拐、顺着海岸线绕过去；海对面是一条白色的小镇和两层山，右边一座白灯塔，天上大朵的积云。
房子、路、海、远山是程序生成的；表面用 Poly Haven 的 PBR 贴图（墙的灰泥、柏油、人行道方砖、混凝土、屋瓦，见下面"材质"），
路灯、木纹、几盆绿植借用公园和咖啡店的。

- **材质**（`vrm/scenes/streetMaterials.ts`）：第一版全是 canvas 平涂的颜色、没有法线，和公园的实拍材质、ez-tree 的树放在一起很突兀，
  换成 Poly Haven 的 PBR 贴图（漫反射 + 法线 + AO/粗糙度，`npm run assets` 下载，CC0）：Plastered Wall 02（墙）、Asphalt 02（路）、
  Square Tiles 03（人行道，放大三倍当 30cm 的方石板）、Concrete Wall 008（路牙、侧沟、矮墙、护岸、电线杆）、Ceramic Roof 01（屋瓦）。
  - 贴图在着色器里按自己的平均色归一（平均色取 1×1 的那级 mipmap），颜色和亮度只由材质颜色定，贴图只给细节 ——
    实拍贴图各有底色（柏油深灰、方砖棕红、灰泥米灰），直接乘颜色要乘到四五倍，对比度跟着放大，第一次换上去路是深灰、人行道发粉
  - 柏油的裂缝提亮（暗部最多到平均的 86%）：原图的长裂缝 3m 重复一次，一条路上一道道一模一样的黑线
  - 屋瓦原图是橙红带青苔的平瓦，转成亮度再乘每栋的瓦色（银灰、蓝灰……）；灰泥的竖接缝压淡，不然像竖拼的木板墙
  - 着色器里加的"旧"：柏油按 1/12 的尺度调深浅（远看不出平铺）、车道上轮胎压过的痕迹、靠路牙那一溜脏；墙根 60cm 的泥、楼板下面的雨痕；
    路牙每 1m 一道缝、矮墙每 1.2m 一块预制块；护岸贴水面那段湿的（暗、光滑）、水线上下一溜青苔
  - 立面图集（窗、门、梁、招牌）盖在灰泥上：按颜色自动算一张遮罩（和墙面底色一样的像素露出灰泥），构件那里不要灰泥的法线
  - 木件（檐口板、檐底、阳台、招牌框）用公园那张旧木板压暗，铁件（支架、旗子的铁臂、格栅、电线杆的横担）提高金属度

- **房子**：开间 × 楼层一格一格拼立面 —— `vrm/scenes/streetTextures.ts` 用 canvas 画一张 2048×1024 的立面图集
  （8×4 格，每格约 2.8m × 3m：咖啡店的大玻璃窗和门、陶器店、暖帘、格子门、卷帘门、玄关、木框窗、铝窗、格子窗、
  落地门、侧墙、山墙、自动售货机……），同样布局的另一张是自发光（店里的暖光、灯笼、售货机的灯箱，遮阳篷的阴影里也是亮的）。

    PMREM（最多 10 次 / 秒），旧的释放。贴图大小和 HDRI 转出来的一样（256），换贴图材质不重新编译

    只有这一档照得到角色；街道的所有材质注入一段循环，算接下来 32 个光源的漫反射（衰减和 three 的点光源一样），路灯下的光斑、店门口被照亮的人行道都是它；
    每个光源一张朝相机的光晕（一个 InstancedMesh，加法混合，也进海面的反射层）。灯在太阳 +4° 到 -5° 之间一盏一盏陆续亮起（亮的那一下闪几下）；
    店的灯按营业时间（商店 22 点、咖啡店 23 点、居酒屋到凌晨 1 点），窗里的店内（室内映射）也按这个开关，住家傍晚七成亮着、夜深了越来越少。
    对岸小镇的盒子侧面按米分格子、随机一部分亮着窗灯（格子比像素还小的时候淡成平均亮度，不然一片闪）；灯塔两道光束 10 秒一圈；
    海面的倒影夜里沿竖直方向抹开，灯在海上拉成光柱；海鸥天黑了不飞
  - 坑：天空着色器里 `pow( dot( a, b ) * 0.5 + 0.5, 2.5 )` —— 两个单位向量的点积会略小于 -1，负数开 2.5 次方是 NaN，只有正背着太阳的一两个像素，
    但烘环境贴图时 PMREM 的模糊把 NaN 摊到了整张图上，所有吃环境光的材质（Lambert 也吃）一片黑，只有角色（MToon 不吃）正常。底数要夹到 0 以上；
    `smoothstep` 的两个边也不能反着给（结果未定义）

  生成场景约 130ms（页面刚打开、JIT 还没热的时候要一两秒）

## Act IR

Jev 输出的不是动画，是一份**表演脚本**。四条轨道各自独立：

```jsonc
{
  "speech": "唔<b:think>……让我想想。这个问题得分两头看<b:turn>，你更关心哪一边？",
  "emotion": { "valence": 0.1, "arousal": 0.45 },
  "tracks": {
    "posture": "idle_alert",
    "expression": [
      { "at": 0,                    "preset": "neutral",  "weight": 1.0, "fade": 0.15 },
      { "at": { "anchor": "think" }, "preset": "sad",     "weight": 0.3, "fade": 0.35 },
      { "at": { "anchor": "turn" },  "preset": "relaxed", "weight": 0.7, "fade": 0.30 }
    ],
    "motion": [],
    "gaze": [
      { "at": 0,                     "target": "camera" },
      { "at": { "anchor": "think" }, "target": "up", "hold": 1.8 },
      { "at": { "anchor": "turn" },  "target": "camera" }
    ]
  }
}
```

两个关键设计：

**时间锚点用 `<b:name>` 而不是秒数。** 做表演决策的那一刻 TTS 还没合成，时长是未知的。
字符位置是语义稳定的，等音频就绪后再换算（`act/anchors.ts`）。锚点名恰好是动作 id 时
自动触发同名动作，否则就是纯时间标记。二期接实时语音流后，用 TTS 的 boundary 事件
持续校正同一套锚点即可，`makeMeasuredMapper` 已经留好了口子。

**词表是闭集。** LLM 自由发挥出来的动作名映射不到 clip 库。枚举定义在 `act/schema.ts`，
`sanitizeAct()` 对越界值就近修正而不是抛错，`jev/actSchemaPrompt.ts` 里的 prompt 片段
由同一份枚举生成，不会漂。

## 配置

编辑 `.env.local`（已 gitignore），**改完重启 dev server**：

```bash
# 判断层：Jev —— 决定"怎么演"。后端按 key 前缀自动识别
JEV_KEY=vck_...                  # 或 sk_...
DEEPSEEK_API_KEY=sk-...          # 输入层：决定"说什么"
```

完整可选项见 `.env.example`。其中 `JEV_REACTION=off` 关掉倾听反应，每轮少一次 Jev 评估。

Jev 有三种接法，端点、鉴权、响应形状都不一样，`server/jev.ts` 按 key 前缀自动分流：

| 前缀 | 后端 | 端点 | 差异 |
|---|---|---|---|
| `vck_` | Vercel AI Gateway | `ai-gateway.vercel.sh/typesafe/v1/systemone` | **必须**带 `model: "typesafe-ai/jev"`；answers 在顶层；计费在 `provider_metadata.gateway.cost`（美元） |
| `sk_` | JevStation | `jevstation.com/api/v1/systemone` | `model` 被忽略；answers 包在 `data` 里；另带 credits 余额 |
| 其它 | TypeSafe 直连 | `api.typesafe.ai/v1/systemone` | 候补名单；形状同 Vercel |

自动识别不对时用 `JEV_BACKEND` / `JEV_BASE_URL` / `JEV_MODEL` 覆盖。

**Vercel AI Gateway 的坑**：免费额度需要先在账户里绑定信用卡才会解锁，否则所有请求
返回 403 `customer_verification_required`。这个错误走的是网关边缘的
`{"error":{"message","type"}}` 形状，和 Vercel 文档里写的扁平 `{message, error_type}`
不是一回事，所以 `jev.ts` 两种都认，解析不出来就把原文透出来。

两层各自独立：只配 Jev 就用规则模板出台词，只配 DeepSeek 则表演回落到规则模板，
两个都不配整条链路照样跑（纯 `MockDecider`）。

### 输入层：DeepSeek

一期用它替代实时语音交互，**只负责"说什么"，完全不碰"怎么演"**。
所以人设（`server/personas.ts` + `server/persona.md`）里只写人格和说话方式，写表情动作是无效的 ——
Act IR 不从这里来。人设和聊天记录见下面的"角色与聊天记录"。

二期接 gpt-live-1 时替换掉的就是这一层（`server/deepseek.ts`），
`judgePerformance` 往右的东西一行都不用改。

延迟是这层的主要成本，所以默认 `deepseek-flash`，且默认**不发**
`thinking` / `reasoning_effort`（官方文档没写 `disabled` 取值，省略最稳）。
要开推理设 `DEEPSEEK_REASONING_EFFORT`。

### 判断层：Jev 是判断模型，不是对话模型

这一点决定了整个接法：**Jev 不生成文本**。它接收一个 `state` 和一组类型化问题，
返回带概率分布和置信度的类型化答案（`POST /api/v1/systemone`）。

这反而比让通用 LLM 吐 Act IR 更合适：

| Jev 的能力 | 在这里的用法 |
|---|---|
| `choice` 的 criteria 是闭集 | 和 `act/schema.ts` 的词表天然对齐，不可能出现"发明了一个不存在的动作名" |
| `choice` 回**整个概率分布** | 直接喂 `ExpressionLayer.setBlend` —— 混合表情白拿。`happy 0.52 + surprised 0.29` 比单一 `happy 1.0` 像人得多 |
| `score` 回级别之间的连续值 | 正好当 blendshape 权重用 |
| `confidence` | 轻度对冲表演幅度（0.75~1.0），**不能重压**，理由见下 |
| `noul` 是 0–1 概率 | 「中途会不会移开视线」→ 概率越高，移开得越久 |

每次评估刻意卡在 **5 个问题以内** —— 文档说超过 5 个问题或 state 超过 8000 字符，
单次评估从 1 credit 变 3 credit。问题是并行评估的，加问题几乎不增加延迟，
所以要加密度时优先考虑的是 credit 而不是时间。

**一句话里的情绪是会变的**（「诶？真的吗！那太好了……不过我有点担心」是惊讶 → 开心 → 担忧），
所以台词按句切成最多 3 段（`act/segments.ts`），**每段单独问一个情绪**，问题随段数变：

| 段数 | 问题 | 推导的（不问） |
|---|---|---|
| 1 | 情绪 · 强度 · 视线 · 姿态 · 会不会移开视线 | — |
| 2 | 情绪 × 2 · 强度 · 视线 · 会不会移开视线 | 姿态 |
| 3 | 情绪 × 3 · 强度 · 视线 | 姿态、移开视线 |

推导的做法和动作一样：从 Jev 已有的答案算（姿态看整句的主导情绪，移开视线看视线分布里
"不看对方"的概率），面板上标「推导」。每段的问题里带上那一段的原文，state 里有整句和上下文，
所以 Jev 判断的是"在这句话、这个语境里说到这一段时"的情绪，不是孤立地给一段字贴标签。

另外还有一次**倾听反应**的评估（2 个问题）：用户话音刚落、角色还没开口时的第一反应，
和输入层写台词**并行**，只看用户说了什么。真人听到一句话，表情先于回答出现。
每轮因此是 2 次评估；不想要就 `JEV_REACTION=off`，回到每轮 1 次。

节拍结构在代码里合成（`src/act/fromJev.ts` 的 `composeAct`），这正是 Jev 文档建议的
"拆成原子问题，用自己的公式组合"：每段开头一个 expression beat，gaze 的进出时机
和动作挂在段落锚点上。

Jev 拿到的 `state` 同时带用户输入和角色要说的话 —— 表演是**回应**，
只看台词判断不出"她是在附和还是在反驳"。

#### confidence 不能拿来重压幅度

踩过一次反向的坑。文档说 confidence 就是从概率分布的形状导出的：集中=高，分散=低。
所以**低 confidence 不等于"Jev 不确定"，而等于"情绪本身就是混的"**。实测：

| 台词 | 分布 | confidence |
|---|---|---|
| 「诶？你居然记得这个」 | surprised 1.00 | 0.99 |
| 「这个功能有三种实现方式」 | neutral 0.96 | 0.95 |
| 「……算了，我也说不清楚」 | sad 0.62 + neutral 0.30 | 0.54 |
| 「哈，行吧。反正我也习惯了」 | sad 0.38 + relaxed 0.31 + angry 0.17 | **0.26** |

最后一条是苦笑，三路混合，语义上完全正确 —— 苦笑就是难过 + 强装轻松 + 一点不甘。
但最初按文档的三档法把低 confidence 压到 0.45 倍，结果情绪最丰富的句子演得最淡：
分布已经用来做混合了，再拿同一个信号去衰减幅度，等于对复杂情绪双重惩罚。

现在只保留 0.75~1.0 的轻度对冲。留一点是因为分布也可能在**对立**情绪之间摊平
（happy 0.5 / angry 0.5），那种脸全给满会很怪。

### 自建服务

想把两层都自己做，就走 passthrough：

```bash
JEV_MODE=passthrough
JEV_ENDPOINT=http://localhost:8787/act
JEV_API_KEY=...                  # 可选，默认发 Authorization: Bearer
                                 # 自定义头用 JEV_AUTH_HEADER=X-API-Key
```

契约 `POST {input, history, draft}` → `ActScript`。UI 右侧「Act IR 契约」面板有完整字段说明。

### key 为什么不放前端

Vite 只把 `VITE_` 前缀的变量注入客户端 bundle —— 反过来说，**任何带 `VITE_` 前缀的
key 都等于公开**，开 DevTools 就能看到。所以这里的变量一律不加前缀，由
`server/jevProxy.ts`（一个 Vite dev-server 中间件）在 Node 侧读取，浏览器只打同源的
`/api/act`，不持有任何凭据。

上线时这个中间件要换成真正的服务端路由——它只在 `vite dev` 下生效，`vite build`
产物里没有它。

不管走哪条路，代理返回前都会过一遍 `sanitizeAct()`：越界值就近夹紧、非法枚举丢弃。
决策层再怎么抽风，角色也不会卡死。

### 聊天记录

- 存在服务端 `data/chats/<session>.json`（gitignored）。输入层的历史**从这里读**，
  前端不用每次把整段记录传上来；刷新页面、换浏览器都接得上
- 每次带最近 40 条、合计不超过 6000 字（`chatStore.recentForModel`）。聊得再久，
  每次请求的长度也有上限。更早的暂时不带 —— 要"长期记忆"就在这里加一段摘要
- 谁写的台词谁记：渐进式管线里台词是服务端写的，`/api/speech` 写完顺手记下这一轮；
  规则模板 / passthrough 模式下由前端 `POST /api/chat/append`
- 测试指令（`测试: …`）和出错时的兜底台词不进记录
- 第一次打开某个角色（或刚重置）时她先打招呼：开场白是固定的，不花钱；
  有 Jev 时照常判断怎么演（1 次评估）
- **重置对话**（聊天记录标题栏右边）：她会忘掉之前聊过的内容。旧记录挪到
  `data/chats/archive/<session>-<时间>.json`，不是删除

接口：

```
POST /api/chat/open   {session}         → {persona, turns, greeted}
POST /api/chat/reset  {session}         → 同上（旧记录已归档）
POST /api/chat/append {session, turns}  → {turns}
```

`/api/speech`、`/api/react`、`/api/judge` 都多了一个 `session` 字段。Jev 的判断仍然只看
前端带上来的最近几轮（`history`），它只需要知道语境，不需要完整记忆。

## 渐进式管线

四个端点：

| 端点 | 干什么 | 失败时 |
|---|---|---|
| `POST /api/react` | 倾听反应：只看用户那句话，和 `/api/speech` 并行 | 返回空，用中性脸开口 |
| `POST /api/speech` | 只出台词（输入层） | 抛错，角色说不出话 |
| `POST /api/judge` | 判断这句话怎么演（按段） | **不抛错**，退回基线表演 |
| `POST /api/act` | 一次性拿完整脚本 | passthrough 模式和不支持渐进的调用方走这条 |

一轮对话的节奏（`App.tsx` 的 `send`）：

```
用户打字      → 倾听：看着对方，眼睛微微睁大
发出消息      → 思考：视线移开（多半往上或侧面）、抿嘴，偶尔瞟回来一下
              ↘ /api/react 并行：第一反应到了就先上脸（还没开口）
台词到了      → 带着第一反应开口：runtime.play(baselineAct(speech, reaction))
整句判断到了  → runtime.upgrade(act)：每一段换成 Jev 判断的情绪
说完          → 余韵：表情留一会儿，再分几段淡成残留的心情
```

实测一轮（Vercel 后端）：用户说「我昨天面试通过了！不过薪水比我预期的低一点……」，
第一反应 happy 0.83，在开口前 0.2s 已经上脸；台词「哎哟恭喜啊！薪水这事儿吧……
低一点是多少？差得太离谱就别急着答应。」被判成 happy 0.91 → neutral 0.76 → neutral 0.87。

`TimelinePlayer.upgrade()` 保留已经走过的时间，把**还没触发**的节拍整体换掉，
已经过去的一次性补齐立即应用。前提是台词和时长一致（`Runtime.upgrade` 里校验，
不一致就放弃升级）—— 否则口型会和台词错位。

判断层是增强而不是硬依赖：Jev 挂了、余额没了、超时，角色照样把话说完，
只是表演停在基线。UI 左上角会亮一条降级提示，原因在右侧面板里。

### 判断层要设超时（实测很重要）

走 Vercel AI Gateway 的延迟方差很大。实测同一条请求连打 6 次：

```
1.03s   19.46s   1.03s   3.81s   2.09s   14.04s
```

多数落在 0.7~1s，但见过 19.5s。Jev 官方宣称比 LLM 快两个数量级，所以这几乎肯定是
网关的排队/冷启动开销，不是模型本身。

这里的要害不是慢，是**过期的判断没有价值**：一句台词只播 3~6 秒，`upgrade()` 只能改
还没触发的节拍，判断回来时台词已经说完就什么都改不了，那次调用纯属浪费。
所以 `JEV_TIMEOUT_MS` 默认 6000，超了就干净放弃、退回基线，
重试也受同一个 deadline 约束（否则退避会把"及时放弃"的意义抵消掉）。

### 同一时刻的表情拍会合并

这是踩过一次的坑，值得单独说。`composeAct` 把 Jev 的概率分布摊成多个 `at` 相同的
expression beat，本意是"这是一张混合的脸"。但渲染层如果对每一拍单独调
`setExclusive`，后一拍会把前一拍清零，分布直接退化成 top-1 —— **混合表情等于白做，
而且从返回的 JSON 上完全看不出来**（JSON 里两拍都在）。

所以 `compileAct` 按解析后的时刻分组，同一时刻的若干拍合成一条带 `mix` 的事件，
渲染层一次 `setBlend`。验证要看 `expressionManager.getValue()` 的真实权重，
光看 Act IR 的 JSON 会漏掉这类问题。

## 谁说了算

前端**没有任何表演参数的控件**。留一个滑块就意味着"到底谁说了算"没有唯一答案，
所以情绪、强度、视线、姿态全部交给 Jev，UI 只做只读展示。

但"全部由 Jev 控制"这句话需要拆开讲，三类东西性质完全不同：

**① Jev 判断的（每句话一次评估）**

| 参数 | 问题类型 | 落到哪 |
|---|---|---|
| 倾听时的第一反应 | choice + score | 开口前的表情，也是基线表演的起点 |
| 每一段的情绪概率分布 | choice × 1~3 | 每段一次 `ExpressionLayer.setBlend` |
| 强度 | score | 权重的整体倍率 |
| 视线目标 | choice | `GazeLayer.look` |
| 待机基调 | choice（1 段时问，否则推导） | `IdleLayer.setPosture` |
| 是否中途移开视线 | noul（≤2 段时问，否则推导） | 中段 gaze beat 及其保持时长 |

**② 自主的不随意行为（不该由 Jev 管，也管不了）**

眨眼、眼球微扫视、呼吸、重心转移、头部微漂移、微表情闪动、口型，
以及几类**不带情绪的对话行为**：

- 倾听 / 思考时的神态（思考时视线回避是对话研究里的经典观察：人组织语言时会避开对方的视线）
- 按标点派生的节奏信号（`timeline.ts` 的 `deriveCues`）：问句末尾眼睛微微睁大、
  感叹字上一闪、句子边界眨眼、笑声词上的起伏
- 情绪的**动力学**：部位错峰、峰值回落、惯性、余韵（见下面的"表情"一节）

这些决定的是"脸怎么动"，不是"什么情绪"。情绪是什么、多强，只来自 Jev。

这些是连续发生的生理层动作，Jev 是**每句话一次**的判断模型：问它"现在该不该眨眼"
既没有语义可判断，也会让成本和延迟完全失控。它们由 `idle.ts` / `expressions.ts` /
`lipsync.ts` 用噪声和随机间隔自行驱动 —— 去掉之后角色会立刻变成会说话的贴图。

**③ 渲染侧的硬编码常量（不是表演决策，是设备标定和合成规则）**

| 常量 | 在哪 | 是什么 |
|---|---|---|
| `INDEX_TABLES` | `faceRig.ts` | 这个模型每个部位形状对应哪个 morph（逐个渲染认出来的） |
| `RECIPES` | `expressions.ts` | 每个情绪由哪些眉 / 眼 / 嘴形状组成 |
| `SHAPE_CAP` | `expressions.ts` | 形状在**这个模型**上的可用上限。笑眼 1.0 是全闭眼，说话时封顶 0.5 |
| `PART_BIAS` / 掩饰规则 | `expressions.ts` | 混合情绪按部位怎么合（见下面"表情"一节） |
| 部位错峰、峰值回落、惯性 | `expressions.ts` | 表情的动力学常数 |
| 混合门槛 `0.15` | `fromJev.ts` | 概率低于此值的情绪不进混合，滤长尾噪声 |
| `confidenceGain` | `fromJev.ts` | 0.75~1.0 的轻度对冲 |
| `bodyMotion 0.25` | `idle.ts` | 半身景别下的肢体动作总量 |

这一类**刻意不交给 Jev**：它们描述的是"这个模型能演到什么程度"和"一张脸怎么动"，
换个 VRM 模型就要重调，而 Jev 对模型一无所知。把它们写进 Jev 的
问题集，等于让判断模型去记每个角色模型的 blendshape 脾气。

调这些值走 `window.__jev`（仅 dev），不进产品 UI。

### 测试指令

拆掉滑块之后，调试用文本指令代替：

```
测试: 开心 90%                          单一情绪
测试: 难过 40% 放松 30%                 混合，验证概率分布真的叠加了
测试: 开心 60% | 今天天气不错            自定义台词
测试: 惊讶 80% > 开心 70% > 难过 40%    一句话里的情绪变化，按台词的段依次对应
测试: 反应 惊讶 70%; 开心 80%           模拟整轮节奏：思考 → 第一反应 → 开口
test: happy 90%                         英文同义
```

分段测试不写台词时会用内置的两段 / 三段台词（「哈，行吧。反正我也习惯了。」
「诶？真的吗！那也太好了吧。」），保证段数和指定的一致。

中文别名认这些：开心/高兴/快乐/笑、生气/愤怒/不爽、难过/伤心/低落/委屈、
放松/温和/平和、惊讶/意外/吃惊/震惊、中性/平静。

要点是它**构造一份合成的 Jev 答案**，再走 `composeAct` —— 和真实链路共用同一份
合成代码（`src/act/fromJev.ts`，为此从 `server/` 挪到了共享层）。
如果测试路径自己另算一套 Act IR，测出来的东西不作数。

跳过 DeepSeek 和真实 Jev：不花钱、不等网络、结果可复现。

### 每一拍都发整个混合，不能只发主导情绪

一个只看 JSON 发现不了的坑。最初一句话摊成三拍（起 / 中段 / 收尾），中段和收尾只发
`dominant`。单一情绪时没问题，但混合表情会在 45% 处被**拍平成主导情绪** ——
苦笑演到半句就变成纯难过。现在每一拍（每一段）都发整个混合。

## 表情

### 分部位合成（`vrm/faceRig.ts`）

VRM 的情绪预设是**整脸烘焙**的：`happy` 一个槽同时改眉、眼、嘴。带来三个问题：
混合情绪只能整脸相加（苦笑 = 两张整脸叠在一起，嘴又哭又笑）；嘴被情绪占了，口型没地方放；
眉眼和嘴的节奏没法分开。

VRoid 导出的脸上其实有分部位的形状，只是 VRM 预设没用。这个模型的 41 个 morph
导出时丢了名字（变成 "0".."40"），VRM 表情只用了其中 15 个。剩下的是**逐个渲染认出来的**：
每个形状单独拉满，眉眼、嘴各截一张特写对比，再和整脸预设交叉验证
（整脸 angry 的嘴 = 23，整脸 relaxed 的嘴 = 25，整脸 sad 的眼 = 18、嘴 = 27）。

| 部位 | 可用的形状 |
|---|---|
| 眉 | 生气 5、难过 8。另外三种（6 / 7 / 9）是**往上抬**的，被厚刘海完全挡住 |
| 眼 | 瞪 11、笑眼 ^^ 15（单眼 16 / 17）、下垂 18、睁大 19、用力闭 20 |
| 嘴 | 闭嘴笑 25、张嘴笑 26、撅嘴 23、抿嘴 24、委屈小开口 27、O 型 28 |

这些形状注册成额外的 VRM 表情（`part:eye_smile` 这样的名字），由表情管理器统一管 ——
直接写 `morphTargetInfluences` 的话，管理器每帧先清零再叠加，顺序一乱就被清掉。
用"预设绑定了哪些下标"做指纹来识别模型；有 `Fcl_*` 名字的 VRoid 模型直接按名字找；
都对不上就退回整脸预设，行为和以前一样。

**这个模型的眉毛基本看不见**（姬发式刘海）。所以表情主要靠眼睛和嘴，眉毛只在生气、
难过这两种往下压的情况下露出来。

### 混合情绪怎么合：上半张脸更诚实

表情研究里的经典观察：下半张脸（嘴）更受意识控制，会用笑去掩饰；上半张脸（眉眼）
更容易泄露真实情绪。所以按部位合成时：

- 眉毛对负面情绪更敏感，对笑意更迟钝（`PART_BIAS`）
- 同时有笑意和负面情绪时，**嘴上的负面再压一半，眉毛上的笑意压一半**
- 嘴上笑和撇嘴不能同时满，弱的一方让出来

效果：sad + happy 合出来是"眉眼委屈、嘴在笑"的苦笑；happy + surprised 是睁大眼的张嘴笑。

### 动力学：一张脸怎么动起来像人

| 做法 | 为什么 |
|---|---|
| 部位错峰：眉 0ms、眼 35ms、嘴 85ms | 真人换表情时眉眼先动、嘴后到，不是整张脸同时变 |
| 临界阻尼弹簧，淡出比淡入慢 1.8 倍 | 起止速度为零；表情消退本来就比出现慢 |
| 峰值回落：到峰值后回落到 84% | 表情不会一直挂在峰值上 |
| 让位给口型 | 发音节时张嘴类的嘴形让出来，字与字之间、标点处回来；说话时笑眼封顶 0.5，不闭死 |
| 感知曲线：上脸幅度 = 语义强度^0.65 | 形状权重和"看起来多明显"不是线性的，温和的情绪（0.3~0.5）线性映射下几乎看不出来 |
| 情绪惯性 | 心情上得快（0.8s）下得慢；当前段情绪很弱时透出一部分心情 —— 说话时 75%、12s 慢慢散，不说话时 45%、6s |
| 余韵 | 说完先留 1.2s，再分两段淡成残留的心情，15s 后归零 |
| 换主情绪时眨眼、句界眨眼 | 真人几乎不会睁着眼把一个表情渐变成另一个 |

情绪惯性是真实对话里测出来的：「哎哟恭喜啊！……低一点是多少？」Jev 判成
happy 0.91 → neutral 0.76，没有惯性时笑容 0.5s 内完全消失，问句是一张空白的脸说出来的。
惯性只在当前段本身情绪很弱时起作用，新来的强情绪不会被上一个情绪污染。

**Jev 的 neutral 是"这一段没有新的情绪"，不是"把脸清空"。** 第一版惯性（45%、心情上升 2s）
在长一点的回复里还是不够：「日本啊，挺好。机票贵是贵在哪儿，直飞还是转机？要是差得不多……」
Jev 判成 relaxed → neutral 0.87 → neutral 0.69，第一段只有 1.7s，心情才涨到一半就被 neutral
接走，9.4s 的一句话从第 2 秒起就是一张空白的脸 —— 看起来就是"表情没了"。现在：

- 说话时惯性 75%、12s 慢慢散：笑着开口，问句时笑意收一些但还在，说到句尾约剩四成
- 比较相邻两段是不是"同一拍"时 neutral 单独看：neutral 0.87 和 neutral 0.69 + relaxed 0.17
  整体很像，可后一段带着前一段没有的笑意，这一拍不能省
- 感知曲线把温和的情绪抬到看得见的程度（0.3 → 0.46、0.5 → 0.64），0.9 基本不动；
  只改幅度，是什么情绪、谁强谁弱仍然是 Jev 说了算

同一份 Jev 判断前后对比：`__filmstrip(act, [时刻…])` 也接受一份 Act，真实对话之后
传 `__jev.act` 就能不花钱重放同一段表演。

### 验收

`__trace('测试指令')` 逐帧推进一轮，每隔一段时间采样对话状态、语义情绪、实际的部位形状、
视线；`__filmstrip('测试指令', [时刻…])` 在指定时刻各截一张脸部特写拼成一张图。
两者都用测试指令的语法，不花钱，结果可复现。

## 动作

以前这里是一套程序化的手势（掩嘴笑、托腮、扶额……手到脸的那几个用 IK 解），
效果不理想，已经整个删掉（在 git 历史里）。现在的动作是**动捕**：VRoid 官方免费的

### 谁决定做不做

和表情一样，情绪是什么、多强由 Jev 决定；`act/motionRules.ts` 只是把 Jev 已有的答案换算成
"要不要动"，不多问 Jev 一个问题。这 7 个都是 7~12 秒的全身展示动作，不是点头摊手的小手势，
所以门槛很高，**不做动作才是常态**。打招呼例外：问候是说话的礼节不是情绪，看台词；
但那一段 Jev 判成难过 / 生气时不挥手（"再见……"不该笑着招手）。
开场白也一样：Vivi 的"欢迎光临！"会挥手，詩乃的"……哦，是你啊"不会。

### 剪辑：在代码里改，不动原文件

规约允许自由修改数据，但文件本身不能再分发，所以剪辑写在代码里（`vrm/motion.ts` 的
`MOTION_FILES`），加载时生效，原 `.vrma` 不动。两种：

- **`trim`**：只保留原片的某一段，预览和对话都用剪过的版本
  - 打招呼：原片 0~1.6s 蹲着（膝盖弯 155°、胯部只有站立时的 35%），1.6~2.4s 跳起来，
    2.6s 才完全站直开始挥手。"先蹲一下再打招呼"很奇怪 —— 剪掉，从 2.6s 开始（剩 4.7s）。
    剪完实测：淡入过程中膝盖最多弯 5°，没有下沉
- **`talk`**：对话里自动触发时只播其中一段（一句台词没有 7~12 秒那么长）
  - 比耶：V 手势从 2.2s 一直举到 9.5s —— 对话里举到 7s 就收

数值是逐个看过全身截图（`__motionstrip`）、读过关键骨骼（胯部高度、膝盖角度）的曲线后定的。
以后要做更细的修改（某几根骨骼的幅度、左右镜像、只要上半身），也在这一层加。

### 和其他层怎么叠

动作层写的是**绝对姿势**：静止姿势和动捕之间按权重 slerp。idle（呼吸、重心、垂手）和
视线的头部跟随是乘在上面的偏移，动作在播时按 `(1 - 动作权重)` 让出来 —— 动捕里已经有
呼吸和重心，再叠一层会重复；视线的头部跟随按"身体面朝前"算，转圈时叠上去会把脖子拧歪。
眼球照样看着你。动作放完淡出，身体回到 idle 的待机里（实测手臂回到和播之前完全相同的姿势）。

没用 `THREE.AnimationMixer`：mixer 在权重 < 1 时向"绑定那一刻的姿势"混合，而那一刻骨骼上
已经叠着上一帧的 idle / 视线偏移，淡入淡出会混向一个过期的姿势。这里直接对每条轨道插值
（`@pixiv/three-vrm-animation` 的 `createVRMAnimationHumanoidTracks` 负责按模型的 hips
高度和 VRM 0/1 轴向换算），自己决定和谁混。换模型时 `.vrma` 不用重新下载，只重建轨道。

同一个动作正在播时不会重来：Jev 的判断晚到时会把已经过去的节拍补一次，没有这条会从头再挥一次手。

### 两层混合：底层循环待机 + 上层动作

`vrm/motion.ts` 有两层：底层是一直循环的待机（首尾交叉淡化），上层是对话触发的动作 / 预览，
整体覆盖在底层上，放完淡回底层。同一层里的交叉淡化按权重归一化混合，**不经过静止姿势** ——
静止姿势是 T-pose，往它混手臂会往上飘一下。

底层现在是 pixiv ChatVRM 的站立待机循环（`IDLE_BASE = 'idle_loop'`）。有它时 idle 层让出呼吸、
重心和垂手，只留 Jev 判断的姿态（开心 / 低落 / 警觉）的微调；情绪越激动播得越快一点（0.92~1.08 倍）。
文件不在时（新克隆的仓库）静默退回原来的程序待机。

### 待机：ChatVRM 的 idle_loop.vrma

- 来源：[pixiv/ChatVRM](https://github.com/pixiv/ChatVRM) 的 `public/idle_loop.vrma`（153KB，**MIT**，
  授权原文放在 `public/motions/chatvrm/LICENSE`）。和 VRoid 的 7 个动作一样是 `.vrma`、为 VRoid 体型的角色做的，
  没有混元那种比例对不上的问题。MIT 允许再分发，明文 `.vrma` 直接入库
- 原片里人站在偏离中心 15.7cm 的地方 → `hips.center` 以平均位置为中心；实际左右晃动只有约 2.8cm
- 原片本身是无缝循环（首尾两帧所有骨骼差 < 0.05°）→ `loop: 'wrap'` 直接绕回开头。交叉淡化反而会
  把相差零点几秒的两个姿势混在一起。实测 25 秒（跨两次接缝）单帧最大转动 0.17°
- 手臂几乎竖直下垂（离竖直 5°），碰到往外蓬的裙摆，手指有一半在裙子里 → 上臂各外展 6°。
  裙子更蓬的模型在 `models.ts` 的 `armOut` 里再加：Vivi 的 A 字连衣裙 +3°，Victoria 的蓬裙 +6°
  （离竖直 17°）。这个额外外展只作用于待机，不影响打招呼、比耶这些动作
- 实测（詩乃）：头部左右 4.1cm、胯部 2.8cm、脚几乎不动（1.7cm）；VRM 0.x（詩乃、Vivi、Victoria）
  和 1.0（AvatarSample_B）上都验证过手不进裙子

### 手：待机时手指的自然弯曲和随机变化，说话时的小动作（`vrm/hands.ts`）

idle_loop 只有手腕、没有手指轨道，VRM 的静止姿势又是 T-pose 的平手 —— 不管的话待机时手指一直绷得笔直、
五指张开、拇指支棱在外面，像两块板子。手指层垫在待机下面，三部分叠在一起：

- **自然弯曲**：放松垂手的样子，从食指到小指越来越弯（近节 14° → 26°，中节、远节跟着弯）、并拢一点，
  拇指收在食指旁边。方向和量级参考 VRoid 官方动捕开头垂手那几帧的手指
- **缓慢漂移**：每根手指各自的伪噪声（±3.5°，6~10s）+ 整只手的松紧（±4°，~16s），手腕再加一点不循环的漂移
  —— 和身体的待机一样一直在微动，两只手各走各的
- **小动作**：每只手隔 7~18 秒随机来一下：轻轻握一下（停一两秒再松开）、食指 / 中指抬一下、拇指在食指侧面蹭两下
- 姿态（Jev 定的 posture）改变松紧：开心时更松更开，低落、警觉时更收；激动程度让漂移和小动作快一点、勤一点
- 上层动作（VRoid 的 7 个动作都带完整的手指）在播时按 `(1 - 动作权重)` 让出来，比耶的 V 手势不受影响
- **说话时**（speech_start → speech_end），手不离开体侧，只做小幅度的"说话的手"：
  - 每句话挑一只主手（多半是右手）：小臂抬起一点（12°）、稍微往前往外、掌心稍微转向前、手指松一点；
    另一只手只跟三分之一
  - **节拍**：落在发声的音节上（口型张开时，停顿处不打），隔 0.7~1.7 秒一下 —— 小臂轻轻一抬（再 +11°）、
    手腕一翘、手指一松。真人说话时的节拍手势（beat gesture），不表达内容，只跟着说话的节奏；有时两只手一起
  - **标点**（timeline.ts 从台词派生的节奏信号，不带情绪）：问号 → 小臂往前送（+24°）、掌心转向对方、手指张开
    （"你说呢"，交出话轮）；叹号 → 更用力的一下，手指收紧；笑声 → 两下轻颤；句末 → 停一拍，有时换另一只手
  - 幅度按全身景别（相机 4m 外）看得出来定的。第一版小臂只抬 6°，手只挪 2~3cm，看上去和待机没区别；
    正面看往前抬是纵深方向，所以带一点往外
  - 幅度和频率跟着 Jev 定的姿态和激动程度：低落时只有一半，开心、激动时多一点、大一点
  - 说话时不做待机的小动作（手在"说话"，不是在发呆）
- 特写对比：`await __hands('hands.jpg', [0, 3, 6])`（每行一个时刻：左右手正面 + 外侧 + 斜 35° 的上半身）。
  边说边截：`await __hands('talk.jpg', [1, 3, 6], '开心 40% | 我跟你说，今天店里来了一只小猫！它就坐在窗台上晒太阳，可爱吧？')`
  （测试指令语法，不花钱；结果存成文件，屏幕上看不到变化）。台词要够长，也别触发动作 —— 开心 ≥ 60% 会比耶、
  "你好"开头会打招呼，动作自带手指和手臂，播的时候手的层让出来；返回值的 `notes` 会提示这两种情况。
  要实时看：聊天框里发同样的测试指令，鼠标滚轮拉到全身。
  VRM 0.x（詩乃）和 1.0（AvatarSample_B）上都验证过手指往掌心弯

### 试过、放弃了的：腾讯混元文生动作（HY-Motion）

腾讯混元生 3D 的 `SubmitHunyuanTo3DMotionJob` 能用一句中文描述生成带骨骼动画的 FBX（约 15 秒出结果，
每次 10 积分）。接进来试了"微笑聆听"和三个待机候选，**放弃了**：

- **比例对不上，一碰身体就穿模**：输出是成年人比例的 SMPL-H 骨架，这些角色肩窄、身体小、裙子蓬。
  按转角换算过来，身体的大姿态还行，但手一靠近身体（交握、垂在裙边）就交叉、陷进裙子。
  能按动作逐个手调（某几根骨骼加偏移），但几乎每个动作都要调；根治要做按手的位置换算（IK）加碰撞，
  又回到了之前效果不好的那条路
- **动作本身常不自然**：同一句"站着待机"，有的一直挪步，有的整个上半身转过去张望，
  开头往往先横跨一步才站定
- 还踩了一个坑：FBX 里静止骨架和动画不在同一个高度基准上（胯部 -19cm vs 97cm），直接相减人会被抬高 1 米多

代码已经删掉（在 git 历史里：`server/tencent3d.ts`、`server/motionGen.ts`、`src/vrm/retargetSmpl.ts`），
生成的文件移到了废纸篓。剪辑层的 `scale` / `offset` / `hips` 和两层混合是通用的，待机循环就用上了。

## 语音

[Qwen3-TTS](https://github.com/QwenLM/Qwen3-TTS)（阿里）。选它的理由：能用一句话指定语气
（「用开心、轻快的语气说」），一句话里按段换语气就靠这个。两种后端，对浏览器是同一套接口：

| 后端 | 什么时候用 | 说明 |
|---|---|---|
| **远程千问**（`server/qwenTts.ts`） | 配了 `DASHSCOPE_API_KEY` 就默认用它 | 模型 `qwen3-tts-instruct-flash`，13 个说普通话的女声系统音色。不占本机内存，以后搬到服务器也只是一个 key |
| 本地（`tts/server.py`） | 没配 key，或 `TTS_BACKEND=local` | mlx-audio 跑在 Apple Silicon 上，4.5~9GB 内存 |

远程：千问 AI 平台和阿里云百炼（国内 / 国际）的 key 都能用，它们是同一套 DashScope 接口、
不同的地址。不指定地址时自动探测：给每个地址发一个缺字段的请求，key 不对的回 401/403、
对的回 400（参数错误），不产生合成、不计费。

浏览器拿到的格式两种后端完全一样（流式 PCM + `X-Sample-Rate`，非流式 WAV），
所以前端的播放、口型、时间轴一行都不用改。音色列表也由服务端给（`/api/tts/health` 的 `voices`）。

下面几节讲的是本地后端；"声音的语气和表情用同一个判断""时间轴跟着真实音频走"两种后端都一样。
试过的方案对比、每种语气的试听见 `tts/bench.py` / `tts/listen.py`（生成 `tts/out/listen.html`）。

### 本地后端：安装（一次）

```bash
/opt/homebrew/bin/python3.13 -m venv tts/.venv
tts/.venv/bin/pip install mlx-audio
```

模型（约 4.5GB）第一次启动时自动从 Hugging Face 下载。之后 `npm run dev` 会自动拉起
`tts/server.py`（日志前缀 `[tts]`），就绪后界面上的开关会变成「语音：vivian（本地 Qwen3-TTS）」
并默认打开。也可以 `TTS_AUTOSTART=off` 之后另开终端 `npm run tts`。

改 `vite.config.ts` 或 `server/*` 触发配置重载时语音服务**不会重启**（新的插件实例探到它
还活着就复用），不然每改一次配置就要重新加载 4GB 的模型。改了 `tts/server.py` 要自己
结束那个 Python 进程，下次配置重载时会用新代码拉起来。

### 音色

界面上的下拉框选，跟着角色记在浏览器里（见"模型"一节），下次打开、换回这个角色时用它（没选过就用 `TTS_SPEAKER`，默认 vivian）。
切换后角色会用新音色说一句，直接听效果。只列女声，分两组：

| 后端 | 分组 | 音色 |
|---|---|---|
| 远程 | 千问系统音色 | 千雪（二次元虚拟女友）、芊悦、苏瑶、十三（Vivian）、茉兔、四月、少女阿月 …… 共 13 个 |
| 本地 | 预设音色 | Vivian、Serena、Ono Anna（日语母语）、Sohee（韩语母语），CustomVoice 的预设说话人 |
| 本地 | 设计音色 | 元气少女、清冷御姐，VoiceDesign 模型按 `tts/voices.json` 里的文字描述生成 |

存下来的选择按 id **不区分大小写**匹配：本地的 `serena` 和千问的 `Serena` 能对上，换后端不丢选择。

设计音色要多加载一个模型，语音服务的内存从约 4.5GB 变成约 9GB（`voices.json` 为空就不加载）。
加新的设计音色：在 `voices.json` 里加一条 `{id, name, desc, prompt}`，重启语音服务。

设计音色的问题是**每次生成都会按描述重新"想象"一次音色**。选这两个是试听后定的：同一段描述
生成两遍，它们的音高只差 3%（预设音色自己是 4~9%），而"温柔姐姐""软萌少女"差了 18~22%，
前后两轮听起来不像同一个人（`tts/design_voices.py`，试听页 `tts/out/voices.html`）。
另外每个设计音色固定一个随机种子（按 id），同一段话每次合成出来完全一样。

一致性的客观指标（MFCC 音色指纹）试过，没通过校准：预设音色自己的分段之间相似度只有 0.21~0.28，
反而低于两个不同的人（Vivian × Serena 0.84）—— 分段的文字和语气都不同，这个指标对内容比对说话人
更敏感。要可靠的数字得用真正的声纹模型（Qwen3-TTS Base 里的说话人编码器，约 2.5GB）。

### 声音的语气和表情用同一个判断

一句话按段合成（和 Jev 按段判断情绪是同一套切分），每段一个语气指令，由这一段的
情绪分布换算（`act/voiceStyle.ts`）：

| Jev 的判断 | 语气指令 |
|---|---|
| happy 0.7 + neutral 0.3，强度高 | 用非常开心、轻快的语气说 |
| happy 0.55 + surprised 0.35 | 用惊喜的语气说 |
| sad 0.45 + relaxed 0.35，强度低 | 用无奈、苦笑着的语气说 |
| angry 0.6 + sad 0.3 | 用又气又委屈的语气说 |
| neutral 为主 | 用自然、亲切的语气说 |

时序上的难点是：第一段要尽快开口，而整句判断还没回来。所以：

- **第一段**：台词一到就合成，语气用 Jev 的倾听反应；**流式**，攒够 0.3s 就开口
- **后面的段**：按需合成。尽量等整句判断拿到这一段自己的语气，等到"再不合成就接不上"
  的那一刻还没回来，就先用倾听反应的语气。合成速度约为实时的 2 倍，后面的段总能在
  前一段播完前备好

### 时间轴跟着真实音频走

有真实语音之后，估算的时长就不用了：

- 时间轴的时钟是音频时钟（`AudioContext.currentTime`）。下一段晚到了、播放顿了一下，表情一起等
- 每合成好一段，用它的真实起止时间重新编译当前脚本（`Runtime.retime`，和渐进升级同一个机制），
  每段的表情切换点落在那一段声音真正开始的时刻
- 口型：此刻念到第几个字由音频时钟换算，嘴张多大由音量决定 —— 停顿、气口、段与段之间
  的空白处嘴会自己合上

### 实测（M2 Max，1.7B bf16）

| 指标 | 结果 |
|---|---|
| 合成速度 | 实时的 1.7~2.4 倍（RTF 0.42~0.59） |
| 第一段首包 | 0.30s（非流式要等整段合成完，1.29s） |
| 发出测试指令到出声 | 0.36s（真实对话再加上 DeepSeek 写台词的约 2s） |
| 流式分块的接缝 | 0（7 块首尾相接） |
| 段起点 ↔ 表情切换点 | 逐段对齐（例：0 / 2.92 / 6.88s） |
| 说话结束 ↔ 音频结尾 | 对齐（11.04s） |

### 接进来时踩的坑

- **校时把"开始说话"弄丢了。** 第一段一排上播放队列就触发校时，那时第一帧还没跑；替换时间轴
  时 `speech_start` 被当成"不参与替换"丢掉，角色整句都停在"倾听"状态、表情层也不知道
  在说话。现在替换时保留还没触发的 `speech_start`
- **段的结束和下一段的开始是同一个字符下标。** 中间隔着一段停顿，换算时会取到前一段的结束时刻，
  下一段的表情比声音早约 0.2s。结束点往前错开 0.01 个字符
- **校时把过去的表情重放了一遍又一遍。** 每排上一段音频就重新编译时间轴，替换时把"已经过去的"
  节拍全部返回重新应用 —— 对渐进升级（内容变了）这是对的，对校时（只是时间变了）不对：
  一句话开头的表情被重放了 4 次，每次都重新冲一次峰值，脸一抽一抽的。现在校时按
  "每种事件已经触发了几个"认出演过的节拍，只返回真正新到期的
- **流式分块不按采样对齐。** 网络分块可能把一个 16bit 采样劈成两半，奇数字节留到下一块
- `afconvert` 在 24kHz 单声道下不接受 96kbps 的 AAC，试听页用 64kbps

## 渲染分层

每帧顺序固定（`vrm/character.ts`）：

```
resetNormalizedPose → motion → idle → hands → gaze → flush → expression → lipsync → vrm.update
```

motion 写绝对姿势（底层循环待机 + 上层对话触发的动作），其余各层只往 `PoseAccumulator` 里加偏移，
互相不知道对方存在。上层动作在播时 idle / 视线按 `(1 - 动作权重)` 让出来；有动捕待机时 idle 只留姿态的微调。这是避免动作打架的关键，
也是"一句话一个表情=PPT翻页"的解药——四条轨道可以在不同时间点各自变化。

一期聚焦半身表情，所以 idle 的肢体动作量默认压到 0.25。

## 踩过的坑

这几条都是这个 demo 里花时间最多的地方，换模型时大概率会再遇到：

**VRM 的静止姿态是 T-pose，不是 A-pose。** 什么都不做会得到一个一直摊着手的角色。
idle 层给了一个"垂手"的基础姿态（约 70°）；动捕动作自带完整姿势，播的时候 idle 让出来。

**`VRMUtils.rotateVRM0()` 会让弹簧骨炸开。** 它把 `vrm.scene` 整体转 180°，
而弹簧骨记录的是上一帧的**世界**位置；旋转后每个关节的世界坐标瞬间跳到镜像位置，
被当成巨大的速度输入。这个模型 `dragForce` 只有 0.05，阻尼极低，于是头发和裙子
会炸成放射状且再也收不回来。必须在旋转之后 `springBoneManager.reset()` 重新播种。
同理，载入时要先把姿态 snap 到位、空跑几帧、再 reset，否则从 T-pose 缓动到垂手的
过程同样会甩飞头发。

**VRM 0.x 的骨骼局部轴与 1.0 差一个绕 Y 的 180°。** 等价于对欧拉角的 X/Z 分量取反
（idle / 视线层的 `axisFlip`；`.vrma` 的换算由 three-vrm-animation 负责）。

**别把上面那个 180° 混进世界空间的方向计算。** 这里有两个不同的 180°：一个是
`rotateVRM0` 加在 `vrm.scene` 上的场景旋转，一个是骨骼局部轴的差异。前者之后
**两种版本的模型在世界空间里都面朝 +Z**，所以"看向某点"的偏航就是
`atan2(dir.x, dir.z)`，不需要任何偏移；后者只影响欧拉角怎么落到骨骼上，由
`axisFlip` 负责。一旦在方向计算里多减一个 π，头就会永远偏着约 20° 且看不出原因
（`gaze.ts` 里留了注释）。

**情绪 blendshape 是整脸烘焙的。** VRoid 的 `happy` 同时改眼睛和嘴，viseme 也改嘴，
叠满就成了打哈欠。现在用分部位形状解决（见"表情"一节）；没有分部位形状的模型退回
整脸预设，这时只能让口型给情绪让位（`mouthOcclusion()`）。

**同一个权重在不同模型上长相天差地别。** 实测这个模型笑眼超过 0.6 就闭成 `^^`。
所以 Jev 给的是**语义强度**，渲染侧有一张模型标定表把它换算成实际可用的权重
（分部位时是 `SHAPE_CAP`，整脸预设时是 `DEFAULT_CEILING`）。
把这层放在渲染侧而不是 prompt 里 —— 换模型时改一张表，Jev 一个字都不用动。

**模型导出时可能丢了 morph 的名字。** 这个模型的 41 个形状全叫 "0".."40"，只能逐个渲染
去认。认的时候注意：预览面板里循环播放的动作会挡住脸，眨眼也可能正好落在截图那一帧上。

**VRM 0.x 没有 `surprised`。** VRoid 把它放在自定义槽 `Surprised`（大写 S）里。
表情名做大小写无关解析，解析不到再降级到最接近的替代。

## 一期的取舍

- **口型不做音素对齐。** 中文要做准得先出拼音再映射 viseme，投入产出比不划算。
  现在按字符哈希选 viseme（口型和台词一一绑定、可复现），标点处强制闭口。
  接 Azure / ElevenLabs 这类能给音素时间戳的 TTS 后，`LipSyncLayer` 直接换数据源即可。
- **语音用本地 Qwen3-TTS。** 只在 Apple Silicon 上跑（mlx-audio）；别的机器或没装时
  回落到浏览器的 Web Speech（拿不到音频流，口型只能按估算时长走）。
- **动作只有 VRoid 官方的 7 个全身动捕。** 对话里高频的点头、摇头、摊手这类小动作还没有；
  以后可以接 Mixamo 之类的动捕（FBX 转换后走同一个动作层），或者 BOOTH 上的 `.vrma`。
